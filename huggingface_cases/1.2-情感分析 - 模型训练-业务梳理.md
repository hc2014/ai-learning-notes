# 1.2 情感分析模型训练脚本：业务流程与知识点梳理

## 一、脚本目标

这个脚本的核心目标，是在本地已下载好的中文评论情感分类模型基础上，做一次“小样本增量微调（fine-tuning）”，让模型更好地识别你自己的业务语义，例如：

- 正面评论：口碑好、服务好、菜品好
- 负面评论：态度差、服务差、表达讽刺或“只会吃”的口语化负面

从业务上看，这个脚本属于：

- 文本分类任务
- 二分类任务
- 本地模型微调
- 典型的中文评论情感分析流程

---

## 二、整体业务流程

### Step 1：准备训练数据

脚本首先构造一个 `data` 列表。每一条数据由两部分组成：

- `text`：原始文本
- `label`：标签

这里的含义是：

- `label = 0`：差评 / 负面
- `label = 1`：好评 / 正面

业务含义很直接：

- “这家店味道太差了，再也不来了” → 负面
- “环境很好，服务也很周到，推荐！” → 正面

这一步是整个训练流程的“数据源”。如果数据质量和覆盖面不够，模型后续即使训练了也会表现得很“表面化”。

### Step 2：构造成 HuggingFace Dataset

脚本通过：

```python
dataset = Dataset.from_list(data)
```

把 Python 列表转换成 HuggingFace 的 `Dataset` 对象。

随后又做了一次切分：

```python
dataset = dataset.train_test_split(test_size=0.2, seed=42)
```

也就是：

- 训练集：用于更新模型参数
- 测试集：用于验证模型是否学会了

这个拆分的目的是为了避免“训练时看见了所有样本，导致评估失真”。

### Step 3：加载本地模型与 tokenizer

这里使用的是本地路径：

```python
checkpoint = "./local_models/roberta-base-finetuned-dianping-chinese"
```

对应的两个核心部件：

- `AutoTokenizer.from_pretrained(checkpoint)`：负责把文本转成模型可读的 token id
- `AutoModelForSequenceClassification.from_pretrained(checkpoint, num_labels=2)`：加载带分类头的模型

这一步意味着：

- 不再重新从头训练一个模型
- 而是在已有的 RoBERTa 中文评论分类模型上继续做“增量训练”

它的好处是：

- 训练速度更快
- 需要的数据更少
- 模型基础能力已经具备

### Step 4：数据预处理

文本不能直接喂给模型，需要先经过 tokenizer：

```python
def preprocess_function(examples):
    return tokenizer(examples["text"], truncation=True, max_length=128)
```

这里关键点有两条：

- `truncation=True`：超长文本自动截断
- `max_length=128`：统一最大长度

然后：

```python
tokenized_datasets = dataset.map(preprocess_function, batched=True)
```

这一步把训练集和测试集都转换成了模型可训练的 token 化表示。

### Step 5：动态补齐批次数据

```python
data_collator = DataCollatorWithPadding(tokenizer=tokenizer)
```

它的作用是：

- 让同一批次的样本长度可以不同
- 自动补齐到同一长度
- 增强训练稳定性

### Step 6：配置训练参数

核心训练设置如下：

```python
training_args = TrainingArguments(
    output_dir="./results/roberta-dianping-finetuned",
    eval_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    per_device_train_batch_size=4,
    per_device_eval_batch_size=4,
    num_train_epochs=5,
    weight_decay=0.01,
    logging_steps=5,
    save_total_limit=2,
    load_best_model_at_end=True,
    metric_for_best_model="accuracy",
    report_to="none"
)
```

这些字段分别代表：

- `output_dir`：训练结果保存路径
- `eval_strategy="epoch"`：每一轮训练结束后做一次验证
- `save_strategy="epoch"`：每一轮结束后保存一个检查点
- `learning_rate=2e-5`：微调常用学习率
- `num_train_epochs=5`：训练轮数
- `load_best_model_at_end=True`：训练结束时选择最好效果的模型

### Step 7：执行训练

```python
trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["test"],
    tokenizer=tokenizer,
    data_collator=data_collator,
    compute_metrics=compute_metrics,
)

trainer.train()
```

这里使用的是 HuggingFace 的 `Trainer`，它封装了：

- 前向传播
- 反向传播
- 梯度更新
- 评估指标回传
- 模型保存

### Step 8：保存训练后的模型

```python
save_path = "./local_models/roberta-dianping-my-finetuned"
trainer.save_model(save_path)
tokenizer.save_pretrained(save_path)
```

这里意味着：

- 模型权重保存到硬盘
- tokenizer 也一起保存
- 后续推理可以直接用新模型路径

### Step 9：重新加载保存后的模型做推理验证

这一步非常关键。脚本不是直接拿训练过程中当前对象做预测，而是：

1. `del model` / `del tokenizer`
2. `gc.collect()`
3. `torch.cuda.empty_cache()`
4. 再从 `save_path` 重新加载

这样做的好处是：

- 验证模型文件确实已经保存完整
- 避免“推理时使用的是训练过程中已占用显存或旧状态对象”的误判

## 三、主要知识点

### 1. 什么是 Fine-tuning（微调）

这是模型训练的常见方式之一：

- 不是从零开始训练一个大模型
- 而是基于一个已经训练好的模型，在你自己的小数据集上继续训练

典型用途：

- 文本分类
- 情感分析
- 文本相似度
- 领域问答

### 2. 为什么要用 `AutoTokenizer` 和 `AutoModelForSequenceClassification`

它们分别负责：

- `AutoTokenizer`：把文本拆成词/子词、对齐词表、映射成 token id
- `AutoModelForSequenceClassification`：把编码后的输入送进编码器，再接分类头输出类别分数

### 3. 为什么要做 `num_labels=2`

因为这是一个二分类任务：

- 正面评论
- 负面评论

因此设置：

```python
num_labels=2
```

### 4. 为什么要 `truncation=True`

避免句子太长导致超出模型支持的长度。

而 `max_length=128` 说明：

- 给定长度上限
- 过长文本会被截断
- 保证 batch 输入可处理

### 5. 为什么要 `DataCollatorWithPadding`

因为不同样本长度不一样，训练时必须有统一长度。`padding` 就是把短句补齐到批次内最长长度。

### 6. 为什么 `TrainingArguments` 很重要

它是训练时的总控参数，决定：

- 学多少轮
- 用多大的 batch
- 学习率多大
- 每轮保存一次还是不保存
- 最终是否优选最佳模型

### 7. 为什么要用 `model.eval()`

在推理时使用：

```python
model.eval()
```

它会关闭 Dropout 等训练阶段随机机制，保证结果更稳定，避免训练时的随机扰动影响测试。

### 8. 为什么要重新加载模型做验证

因为：

- `trainer.save_model()` 保存的是模型文件
- 训练对象本身并不等于“最终可独立部署”的模型
- 重新从磁盘加载，才更像真实部署场景

## 五、当前脚本中的典型语义问题

这份脚本的示例数据里，有一类很典型的语义：

- “你看看你一天天的就知道吃”
- “一天到晚就知道吃，啥也不干”
- “除了吃你还会干什么？”
- “就知道吃，胖成这样了”

这些句子都属于：

- 口语化
- 带讽刺或负面评价
- 非标准模板表达

它们的共同点是：

- 词不是单纯正向或负向词
- 但整体语义是负面

因此，模型如果样本量不够，就可能无法稳定学会这类“整体语义判断”。

这也是本次训练里最值得关注的核心点之一。

## 七、其他替代方案

针对大模型，但是小规模特殊数据需要重新训练，往往结果不如人意，往往会出现“我明明给的数据是负面的为什么输出的结果还是正面”的情况，在小规模数据下，模型微调效果不佳是非常普遍的现象。大模型拥有庞大的参数，极少量的数据往往无法扭转其原有的认知，甚至容易导致过拟合。

针对这种情况，业界通常不会死磕“重新训练”，而是会采用以下几类替代方案来解决：



### 1. 改变训练策略：最大化数据利用率

如果一定要训练，可以通过以下技术手段让小数据集发挥最大价值：

* **数据增强（Data Augmentation）**：通过对现有样本进行修改（如文本的同义词替换、句子打乱），人工扩展数据集的多样性。
* **样本加权（Row Wise Weighting）**：在训练过程中，专门为你希望模型学会的“难例”或特定子集提高权重，让模型在学习时给予它们更多关注。
* **交叉验证与早停（Early Stopping）**：使用K折交叉验证进行可靠评估，并在验证集性能不再提升时果断停止训练，防止模型在少量数据上“学过头”（过拟合）。
* **替代正则化**：通过调整学习率、权重衰减等参数组合，限制模型复杂度，避免模型去“死记硬背”噪声。

### 2. 引入外部知识：RAG（检索增强生成）

如果微调无法让模型记住新的业务规则或特定词汇，**RAG 是目前最推荐的替代方案**。

* **原理**：不改变模型本身的参数，而是将你的新数据（如特定的负面评价案例）存入外部知识库。在模型预测或生成时，先从知识库中检索相关信息，作为上下文提供给模型。
* **优势**：成本极低，不需要消耗算力重新训练，且知识可以随时动态更新。

### 3. 知识蒸馏（Knowledge Distillation）

如果大模型微调不动，可以尝试“降维打击”：

* **逐步蒸馏（Distilling Step-by-Step）**：利用大语言模型（LLM）的推理能力，让它不仅给出标签，还给出“推理理由（Rationale）”。将这些带有逻辑推理过程的知识，蒸馏给一个参数量极小的模型（如 770M 参数）。研究表明，这种方式在极少数据下，小模型甚至能超越千亿级大模型的表现。

### 4. 错误分析与定向优化

不要盲目增加训练轮数，而是应该对模型预测错误的样本进行系统性的归因分析：

* **难例挖掘（Hard Example Mining）**：优先把那些模型反复预测错误、最不确定（置信度低）的样本挑出来，进行人工修正或补充标注，再针对性地加入训练集。
* **业务归因**：深入分析为什么这个子集表现不佳。是因为数据采集有偏差，还是现有的特征无法捕获这类数据？有时候这更像是一个商业逻辑问题，而非单纯的算法微调问题。

### 5. 探索前沿的小样本训练范式

学术界也在不断突破小样本的极限，例如：

* **TRAPO 框架**：通过追踪模型在处理样本时的“学习轨迹”，找出那些学习模式与少量标注样本相似的无标注样本，让它们也参与到教学中，从而用极少数据获得强大的推理能力。
* **元学习（Meta-Learning）**：让模型学习“如何快速适应新任务”，从而在有限的数据集上迅速收敛。





## 八、总结

这份脚本本质上是一个“中文文本情感分类微调示例”，核心逻辑非常清晰：

1. 准备业务数据
2. 组织成 `Dataset`
3. 加载本地基础模型 + tokenizer
4. 对文本做 token 化与 batch padding
5. 配置训练参数
6. 用 `Trainer` 训练模型
7. 保存模型与 tokenizer
8. 从硬盘重新加载验证效果

从工程角度看，它既是：

- 一个模型训练脚本
- 也是一个本地部署验证脚本

从业务角度看，它用于：

- 把“通用情感模型”转化成“你自己的业务评论情感模型”

这也是很多 NLP 实战中最经典的一条路线：

“用预训练模型做基础能力，用你自己的小样本做业务适配。”

针对小规模特定情况的样本：我强烈建议尝试 **RAG 方案**，或者在训练时采用**样本加权**和**难例挖掘**，这比盲目增加 Epoch 要高效得多。
