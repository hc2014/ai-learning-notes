# LangSmith 测试与评估脚本流程梳理

本文档用于梳理 [CASE-投顾AI助手（效果评估）/2-langsmith_testing_evaluation.py](CASE-投顾AI助手（效果评估）/2-langsmith_testing_evaluation.py) 的业务逻辑、核心技术点以及这些技术在实际业务中的应用方式。

---

## 1. 脚本的业务定位

这个脚本的作用不是直接生成投顾回答，而是“为投顾 AI 助手做质量评估和回归测试”。

它围绕一个核心目标展开：

- 让智能体在一组预设测试问题上执行
- 记录每次运行结果
- 用 LangSmith 对结果做自动评估
- 形成可比较的实验结果，帮助判断模型、提示词或业务逻辑是否变好

它本质上是一个“评测框架脚本”，用于支撑 Agent 的上线前验证和持续优化。

---

## 2. 业务流程梳理

### 2.1 初始化评测环境

脚本首先检查环境变量：

- LANGSMITH_API_KEY
- LANGCHAIN_TRACING_V2

如果条件满足，就初始化 LangSmith 客户端，后续所有测试和评估结果都会上传到 LangSmith 平台。

这一步的作用是：

- 打开可追踪的执行链路
- 把每次 Agent 调用与测试结果落地到平台
- 方便后续分析问题和比较版本效果

### 2.2 定义测试用例

脚本中把测试场景分为三类：

1. 反应式测试用例
   - 适用于简单、快速响应的问题
   - 例如市场行情、组合占比、ETF 概念解释

2. 深思熟虑测试用例
   - 适用于复杂分析、长期规划的问题
   - 例如经济衰退下的资产配置、退休规划、教育金规划

3. 边界测试用例
   - 用来验证系统对异常输入的鲁棒性
   - 例如空查询、超长查询

这些测试用例本质上是“评测数据集”的雏形，类似产品上线前的回归测试集。

### 2.3 创建或使用测试数据集

脚本会调用 LangSmith 的数据集能力，把上述测试用例写入数据集：

- 如果数据集已经存在，就继续使用
- 如果不存在，就创建新的数据集
- 然后把测试用例作为 Example 添加进去

这一阶段的作用是把“测试输入”变成可重复执行的标准样本。

### 2.4 运行 Agent 测试

脚本会把每个 Example 作为输入，调用主智能体模块 [CASE-投顾AI助手（效果评估）/1-hybrid_wealth_advisor_langgraph_langsmith.py](CASE-投顾AI助手（效果评估）/1-hybrid_wealth_advisor_langgraph_langsmith.py) 中的 run_wealth_advisor。

也就是说，评测不是单纯测试字符串，而是直接把真实业务逻辑跑一遍：

- 读取用户问题
- 根据客户画像判断查询类型
- 选择反应式或深思熟虑处理模式
- 生成最终回答

这使得评测结果更贴近真实业务表现。

### 2.5 使用自定义评估器打分

脚本定义了两个评估器：

- ProcessingModeEvaluator
  - 检查智能体是否正确选择了处理模式
  - 例如“简单问题应走 reactive，复杂问题应走 deliberative”

- ResponseCompletenessEvaluator
  - 检查回答是否覆盖了预期关键词
  - 评估最终响应内容是否足够完整

这一步是脚本最关键的环节：它把“业务期望”转成可量化的评分。

### 2.6 生成实验结果并对比版本

评估执行完后，脚本会把结果提交到 LangSmith 的实验记录中。随后可以：

- 查看单次运行细节
- 查看各项评估指标
- 对比不同实验的平均得分

这对业务来说非常有价值，因为可以持续判断：

- 新提示词是否更好
- 新模型是否更稳定
- 新业务逻辑是否减少错误

## 3. 主要使用的技术点

### 3.1 LangSmith Client

技术作用：

- 连接 LangSmith 平台
- 管理数据集、测试样本和实验记录

在脚本中的使用方式：

- 初始化 client
- 创建或读取 dataset
- 创建 example
- 读取实验运行数据

### 3.2 LangSmith Dataset / Example

技术作用：

- 把测试输入组织成标准化数据集
- 让评测过程具有可重复性和可管理性

在业务中对应的意义：

- 相当于“回归测试集”
- 以后每次改模型、改提示词、改流程时都能复用同一套数据

### 3.3 LangSmith evaluate

技术作用：

- 批量执行测试函数
- 对每一次运行自动触发评估器
- 生成实验结果

这是整个脚本最核心的能力。它让“人工手动测几个例子”升级为“批量、可追踪、可对比”的自动化评测。

### 3.4 RunEvaluator 自定义评估器

技术作用：

- 让评测逻辑不只停留在“是否报错”，而是能衡量业务质量

脚本通过继承 RunEvaluator 自定义了两类评估逻辑：

- 处理模式是否正确
- 回答是否包含关键内容

这相当于把业务规则固化成评估标准。

### 3.5 动态导入主智能体模块

技术作用：

- 通过 importlib.util.spec_from_file_location 动态加载另一个 Python 文件
- 避免文件名以数字开头时常规 import 的问题

这属于工程实现层面的技术点，主要是为了让脚本能直接调用主业务逻辑。

### 3.6 环境变量驱动配置

技术作用：

- 让脚本在不同环境下灵活启用或禁用评测能力
- 避免把密钥写死在代码中

实际使用中，脚本会根据环境变量判断是否真正启用 LangSmith。

## 4. 这些技术在实际业务中是怎么使用的

### 4.1 作为上线前质量门禁

在 Agent 上线前，可以用这套评测流程跑一遍一组关键样本：

- 确保简单问题仍然能快速响应
- 确保复杂问题仍然会走深思熟虑流程
- 确保回答内容含有关键关键信息

如果某次修改导致评分下降，就说明可能影响了业务质量。

### 4.2 作为模型或提示词版本对比工具

业务中经常会发生以下情况：

- 换了一个模型
- 改了提示词模板
- 改了路由逻辑

这时可以用同一批测试数据，跑出不同版本的实验结果，对比：

- 处理模式命中率
- 回答完整度
- 是否更稳定

这比“只看几个示例”更科学。

### 4.3 作为回归测试平台

当业务规则发生变化时，例如：

- 新增了某类客户问题
- 调整了复杂问题的处理策略
- 发现某类查询经常出错

可以把这类问题加入测试数据集，持续保证不会回退。

### 4.4 作为可追溯的调试辅助

LangSmith 的价值不只是评估，还在于可追溯：

- 可以看到每次调用的输入输出
- 可以回看中间步骤
- 可以定位问题是模型、提示词还是业务逻辑引起的

这对 Agent 的迭代尤其重要，因为 LLM 系统的错误往往不容易一步定位。

---

## 5. 这个脚本的价值总结

这个脚本把“AI 助手的业务效果”从一个模糊的主观感受，变成了一个可重复、可追踪、可量化的评测流程。

它的核心价值在于：

- 把业务需求转成测试样本
- 把评估规则写成自动化判分逻辑
- 把结果沉淀到 LangSmith 平台
- 形成稳定的迭代优化闭环

对于投顾 AI 助手这类需要较高可靠性的业务场景，这种评测机制非常关键。

---

## 6. 一句话理解

这个脚本的本质，是“用 LangSmith 给投顾 AI 助手做自动化测试和质量评估的实验平台”。
