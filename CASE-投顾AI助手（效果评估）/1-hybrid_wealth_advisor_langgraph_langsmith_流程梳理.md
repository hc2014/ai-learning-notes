# Hybrid Agent 投顾 AI 助手流程梳理

本文档用于梳理 [CASE-投顾AI助手（效果评估）/1-hybrid_wealth_advisor_langgraph_langsmith.py](CASE-投顾AI助手（效果评估）/1-hybrid_wealth_advisor_langgraph_langsmith.py) 这个 Agent 的业务执行流程、主要技术点以及它们在实际业务中的作用。

---

## 1. 这个 Agent 是什么

这是一个“混合型财富顾问智能体”，通过 LangGraph 构建工作流，结合两种处理模式：

- 反应式处理：适合简单、即时的问题
- 深思熟虑处理：适合复杂、需要分析和规划的问题

它的业务目标是：

- 根据用户提问判断其复杂程度
- 选择合适的处理路径
- 为用户提供更专业、更贴近真实投顾场景的回答

---

## 2. 业务执行流程

### 2.1 输入阶段

当用户输入问题时，脚本会先准备一个初始状态对象，包含：

- 用户问题：user_query
- 客户画像：customer_profile
- 当前处理阶段：current_phase
- 处理模式：processing_mode
- 结果字段：final_response、analysis_results 等

这个状态对象是整个 Agent 的“运行上下文”，类似一个业务流程表。

### 2.2 评估阶段：判断问题类型

第一个节点是 assess_query。

它的作用是：

- 让 LLM 判断用户问题属于哪一种类型
- 确定应该走哪一种处理模式

具体判断内容包括：

- query_type：emergency、informational、analytical
- processing_mode：reactive、deliberative

这一步相当于 Agent 的“分流器”。

### 2.3 反应式分支：快速回答

如果判断结果是 reactive，Agent 会走 reactive_processing 节点。

这一分支适合以下场景：

- 今天市场行情如何
- 投资组合里某类资产占比多少
- ETF 是什么

处理方式是：

1. 先让 LLM 生成一个初步回答
2. 判断是否需要调用工具
3. 如果问题涉及上证指数，就调用 query_shanghai_index 工具
4. 把工具返回结果和用户问题一起再生成最终答案

这一阶段体现了“工具调用 + 轻量推理”的模式。

### 2.4 深思熟虑分支：复杂分析

如果判断结果不是 reactive，而是 deliberative，则 Agent 会进入深度分析链路：

1. collect_data：收集分析所需的数据
2. analyze_data：进行投资分析
3. generate_recommendations：生成最终建议

这条链路更像“投顾顾问”的工作流：

- 先收集背景信息
- 再分析客户资产配置、风险偏好和目标
- 最后生成个性化建议

### 2.5 输出阶段

最后进入 respond 节点，直接返回最终响应。

如果整个流程顺利，最终结果会被写入 final_response；
如果中间出错，则会把错误信息写入 state 中并返回。

## 3. 这个 Agent 的核心业务逻辑

### 3.1 任务分流

这是整个 Agent 最关键的业务能力之一。

它不是简单地对所有问题都做深度分析，而是先判断问题类型，再决定：

- 是快速回复
- 还是进入专业分析

这能显著提高系统效率，也让复杂场景更有专业性。

### 3.2 客户画像驱动

Agent 不是“无上下文”的回答，而是依赖客户画像进行个性化处理。

例如：

- 风险承受能力不同，建议会不同
- 投资期限不同，资产配置建议会不同
- 财务目标不同，推荐策略也不同

这让回答更贴近真实的财富管理场景。

### 3.3 工具调用能力

在反应式分支中，Agent 可以识别是否需要调用查询工具。

虽然这个示例中的工具是“模拟版”，但它体现了一个实际业务中非常重要的能力：

- 让 Agent 不仅依赖模型内部知识
- 还能调用外部信息源

这在真实业务中很常见，比如行情查询、订单查询、政策查询等。

### 3.4 结构化输出与流程编排

该脚本中使用了多种结构化提示词和输出解析：

- 用 JSON 结构约束 LLM 的输出
- 用状态对象保存中间结果
- 用 LangGraph 连线组织多步骤执行

这让业务流程更清晰，也更容易维护和扩展。

## 4. 主要使用的技术

### 4.1 LangGraph

这是整个 Agent 的核心编排框架。

作用：

- 把多个处理节点组织成一张状态图
- 管理节点之间的执行顺序
- 根据条件决定走哪条分支

在这个脚本中，LangGraph 的作用是把“评估 → 处理 → 输出”变成一个可运行的工作流。

### 4.2 Prompt Engineering

脚本中定义了多个提示词模板，例如：

- ASSESSMENT_PROMPT：负责判断问题类型和处理模式
- REACTIVE_PROMPT：负责快速回答
- DATA_COLLECTION_PROMPT：负责收集分析数据
- ANALYSIS_PROMPT：负责做深度分析
- RECOMMENDATION_PROMPT：负责生成最终建议

作用：

- 指导 LLM 按照业务要求输出结构化结果
- 降低模型“胡说八道”的风险
- 让不同模块职责更加清楚

### 4.3 大模型调用

该脚本使用 Tongyi / Qwen 模型调用 LLM。

作用：

- 负责理解用户问题
- 生成分类判断
- 生成回答和分析内容

在实际业务中，这一层就是 Agent 的“智能核心”。

### 4.4 Output Parser

脚本使用了：

- JsonOutputParser：把 LLM 输出解析成 JSON
- StrOutputParser：把 LLM 输出解析成纯文本

作用：

- 让模型输出更容易被程序消费
- 避免把 LLM 的原始文本直接拿来做业务逻辑

### 4.5 Pydantic 数据结构

脚本定义了 CustomerProfile、EmergencyResponseOutput、InvestmentAnalysisOutput 等模型。

作用：

- 给业务对象提供固定结构
- 让上下游数据更规范
- 提升代码可维护性和可扩展性

### 4.6 LangSmith

LangSmith 用于追踪和调试 Agent 的执行过程。

作用：

- 记录每次调用的输入和输出
- 查看每个节点运行情况
- 帮助定位性能问题或逻辑问题

在实际业务中，这对于 Agent 的优化非常重要，因为 LLM 系统难以像传统代码那样直接调试。

## 5. 这些技术在实际业务中的使用方式

### 5.1 作为客服/投顾助手的分流器

在真实业务中，用户问题可能是：

- 简单咨询
- 账户问题
- 复杂投资建议

Agent 先判断问题类型，再决定是快速回复还是深度分析，这样既能提高响应速度，又能保证复杂问题的质量。

### 5.2 作为个性化投顾服务引擎

客户画像不是“附加信息”，而是核心输入。

在真实业务里，财富管理服务必须考虑：

- 客户风险偏好
- 投资期限
- 资产规模
- 目标

所以这个 Agent 的设计非常符合真实投顾场景。

### 5.3 作为具备工具能力的智能体

在实际业务中，Agent 不仅能“说”，还可以“查”。

例如：

- 查行情
- 查账户信息
- 查产品信息
- 查政策规则

这使它不只是聊天机器人，而是一个能辅助业务操作的智能体。

### 5.4 作为可观测的 AI 系统

LangSmith 的加入让这个 Agent 不再只是一个“黑盒”。

在生产环境中，团队可以通过它：

- 跟踪每一次调用
- 找到慢节点
- 发现错误原因
- 评估模型和提示词改动后的效果

---

## 6. 这个 Agent 的价值总结

这个 Agent 的核心价值不只是“回答问题”，而是把一个传统的投顾咨询流程，变成了一个可编排、可追踪、可扩展的智能体工作流。

它的优势包括：

- 兼顾速度和深度
- 能根据问题复杂度做动态分流
- 能结合客户画像做个性化建议
- 能通过工具补充外部信息
- 能通过 LangSmith 进行可观察性管理

---

## 7. 一句话理解

这个 Agent 本质上是一个“基于 LangGraph 的混合型投顾智能体”，它通过任务分流、客户画像理解、工具调用和多步推理，完成从简单咨询到复杂投资建议的业务处理。
